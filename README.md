# npa-ocr

Распознавание сканов без текстового слоя в DOCX: гибридная схема Tesseract (обычный
текст) + Table Transformer/TATR (структура таблиц) + PaddleOCR (структура, через
PPStructureV3) + RapidOCR (текст в ячейках таблиц, ONNX — не падает на CPU без AVX2,
см. `docs/plan.md`). Опционально — ИИ-эскалация текста под печатью/штампом/подписью
через локальную VLM (`--ai-escalation`, см. ниже).
Выделено из [npa-pipeline](https://github.com/EduardIbatullin/npa-pipeline) в
отдельный проект 2026-10-12, чтобы использоваться самостоятельно или в связке с
другими проектами — пакет не знает о НПА-специфике загрузчика, только принимает
путь к PDF.

Подробности реализации, история экспериментов с таблицами и калибровка порогов —
[`docs/plan.md`](docs/plan.md) (перенесено из `docs/stage3-plan.md` npa-pipeline
как есть; часть текста ссылается на прежнее расположение в монорепозитории).

## Установка

```bash
# ядро + тесты (юнит-тесты работают на фейковых движках, без тяжёлых моделей)
pip install -e ".[dev]"

# + реальные модели таблиц и распознавания (PaddleOCR, PaddlePaddle, torch —
# несколько ГБ, модели скачиваются при первом запуске)
pip install -e ".[models]"
```

Системно нужен Tesseract с русским языком (`tesseract-ocr` + `tesseract-ocr-rus` /
`winget install tesseract-ocr.tesseract`).

Или Docker — образ собирает Tesseract и CPU-сборку torch/torchvision (несовместимость
версий между CPU torch и torchvision из PyPI уже обойдена в Dockerfile):

```bash
docker build -t npa-ocr .
docker run --rm -v "$PWD":/data npa-ocr /data/scan.pdf --out /data/out.docx
```

Пик памяти при реальном распознавании не измерен точно, но превышал 12 ГБ на
реальном документе — для контейнера нужно не меньше этого, лучше с запасом
(`docker run --memory 24g ...`).

## CLI

```bash
npa-ocr scan.pdf --out result.docx --authority-name "Правительство Российской Федерации"
npa-ocr scan.pdf --out result.docx --pages-dir run/pages      # папка постраничных результатов
npa-ocr scan.pdf --out result.docx --no-resume                # пересчитать все страницы
npa-ocr scan.pdf --out result.docx --min-free-mb 0             # отключить защиту памяти
npa-ocr scan.pdf --out result.docx --ai-escalation              # восстановить текст под печатью/штампом через VLM
npa-ocr scan.pdf --out result.docx --table-engine vlm           # таблицы через DeepSeek-OCR в vLLM (GPU)
npa-ocr scan.pdf --out result.docx --no-auto-rotate              # не поворачивать страницы по OSD
```

`--table-engine vlm` — таблицы через DeepSeek-OCR в vLLM на GPU (~7 с на страницу
вместо минут у TATR на CPU) со структурой по линиям скана, см. `src/npa_ocr/vlm_tables.py`.
Адрес — `VLLM_URL` (OpenAI-совместимый `/v1`). Если vLLM не ответил, таблицы до конца
документа идут прежним путём (`tatr`), причина — в таймингах. Таблица, продолжающаяся на
следующей странице, сшивается в одну (`src/npa_ocr/table_stitch.py`). Сомнительные ячейки
(текст только от Tesseract и т. п.) дочитываются DeepSeek-OCR по кропу ячейки
(`src/npa_ocr/vlm_reread.py`); недочитанные остаются жёлтыми. В сервисе vLLM стоит за
шлюзом `python -m npa_ocr.vlm_gate`: он запускает контейнер vLLM по первому запросу и
останавливает после `VLM_IDLE_MIN` минут простоя (GPU общая). Пример — сервисы `vlm` и
`vlm-gate` в docker-compose npa-downloader. Для HTTP API движок задаёт переменная
`NPA_OCR_TABLE_ENGINE` сервиса (по умолчанию `tatr`).

Страницы-сканы перед распознаванием поворачиваются по Tesseract OSD (альбомные
таблицы, лежащие на боку); `--no-auto-rotate` отключает поворот.

Распознаются только страницы без текстового слоя — страницы с текстом берутся как
есть. `--authority-name` включает восстановление формулы должности подписанта,
если печать повредила строку («Председатель Правительства…») — поддержаны
Правительство РФ и Президент РФ; ФИО подписанта никогда не восстанавливается.

`--ai-escalation` (по умолчанию выключено) — находит печати/штампы/э-подписи
(дёшевая эвристика + подтверждение локальной VLM, Ollama `qwen3-vl:8b`) и
восстанавливает текст, который они перекрывают; собственное содержимое меток типа
«визуальный мусор» (например, штамп э-подписи) исключается из текста. Требует сеть
до Ollama — адрес берётся из `OLLAMA_URL` (по умолчанию `http://localhost:11434`).
Заметно медленнее на страницах со штампами. Подробности — `docs/plan.md`, раздел
«ИИ-эскалация».

Вместе с `--table-engine vlm` эскалация устроена иначе (`src/npa_ocr/vlm_marks.py`):
qwen3-vl находит рамки штампов, печатей и подписей (первая и последняя страница,
страницы со скоплением неуверенных слов или с картинкой DeepSeek не на месте герба).
Текст меток выкидывается целиком. Слова документа у меток сверяются с ответом
DeepSeek-OCR на страницу, уже полученным для таблиц. Шапка органа под краем штампа
дописывается по `--authority-name`. Модель — `NPA_OCR_MARKS_MODEL` (по умолчанию
`qwen3-vl:8b`). Если Ollama недоступна, документ распознаётся дальше без чистки.

### Внешний контракт (для интеграции с другими проектами)

Это основа, на которую можно полагаться при встраивании `npa-ocr` в другой сервис
(например, фоновое задание с опросом прогресса):

- **stdout**, после завершения — один JSON-объект:
  `{"docx": "...", "pages": N, "pages_ocr_applied": M}` (код возврата 0), либо при
  нехватке памяти `{"status": "insufficient_memory", "message": "..."}` (код 1).
- **stderr**, по ходу работы — строки прогресса и тайминги:
  - `[ 23.8%] страница 5 из 21: распознаётся` / `готово` / `текстовый слой` /
    `взято из сохранённого прогона`
  - `  [стр. 5] таблицы: структура и текст ячеек: 1 мин 39 с` — тайминг шага
  - кодировка — то, что задано в окружении процесса (`PYTHONIOENCODING`); если не
    задано, на Windows при перенаправлении в файл это обычно cp1251, не UTF-8
- **на диске**, рядом с `--out`: `<out>.pages/page_NNNN.json` (сырые результаты
  страниц — переиспользуются при повторном запуске того же PDF с теми же
  параметрами), `<out>.timings.json` (тайминги по шагам).

Формат этих строк и файлов — тесты `tests/unit/test_cli.py` и `tests/unit/test_ocr.py`.

## HTTP API

Тот же образ, другой вход (см. Dockerfile, «Docker» выше) — асинхронные задания
поверх CLI (сервис запускает `npa-ocr` подпроцессом сам у себя — self-exec, см.
`src/npa_ocr/job_runner.py` — падение/OOM в подпроцессе не роняет сам сервер).
Не знает о конкретном потребителе — принимает PDF файлом, отдаёт DOCX файлом;
задуман для использования из любого проекта, которому нужно распознавание скана.

Одновременно выполняется не больше одного задания (тяжёлые модели в памяти,
см. «Установка» выше) — `POST /jobs` отвечает `409`, пока предыдущее ещё `running`.

```bash
# задание
curl -F "file=@scan.pdf" -F "authority_name=Правительство Российской Федерации" \
     http://localhost:8000/jobs
# -> {"job_id": "..."}

# прогресс (тот же набор полей, что в контракте CLI, см. выше)
curl http://localhost:8000/jobs/<job_id>
# -> {"status": "running", "percent": 23.8, "page": 5, "total_pages": 21, ...}

# результат — только когда status == "done"
curl -o result.docx http://localhost:8000/jobs/<job_id>/result

# отмена
curl -X POST http://localhost:8000/jobs/<job_id>/cancel
```

`GET /health` — простая проверка живости, без побочных эффектов.

## Тесты

```bash
pytest                 # юнит-тесты на фейковых движках, без сети и без тяжёлых моделей
pytest -m live          # реальный прогон на настоящем скане (нужны PaddleOCR/Tesseract, минуты)
```

## Ограничения

- Таблицы без линий сетки распознаются TATR неточно (см. `docs/plan.md`, «Открытые
  проблемы»).
- Формулы распознаются как часть текста, не восстанавливаются отдельно.
- Печати/подписи искажают текст под ними; низкая уверенность распознавания
  выделяется жёлтым в DOCX, но не исправляется автоматически.
- Пик памяти при реальном распознавании (PaddleOCR + TATR) — несколько ГБ на
  процесс; точный максимум не измерен, см. `docs/plan.md`.
