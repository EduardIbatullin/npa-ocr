# Этап 3 — OCR документов без текстового слоя

Предварительный план, в процессе эмпирической проверки на реальных документах (начато 2026-10-01). Не финальная версия — решения по механизму распознавания таблиц ещё уточняются.

## Цель

Получить текст документов, у которых официальный PDF — скан без текстового слоя, с точностью, близкой к 100%. Без ИИ в рантайме (в смысле LLM) — используются локальные OCR-модели, не облачные API с оплатой за запрос.

## Охват (сужен по итогам проверки реальных данных)

- **ИТС/НДТ приказы Росстандарта** — вне скоупа. Решение пользователя: пока считаем, что достаточно самого справочника ИТС, приказ не обязателен; если понадобится отдельно — решать отдельно, когда возникнет необходимость.
- **Справочники ИТС** — почти всегда уже содержат текстовый слой (проверено на 7 реальных файлах: 0–1 страница без текста из 147–418, похоже на обложку, не скан) — реальных кандидатов на OCR среди них практически нет.
- **НПА с `publication.pravo.gov.ru`** — вот где OCR реально нужен. Проверено на 3 реальных документах (Постановление Правительства, Приказ Минприроды, Федеральный закон) — **все три полностью сканы, без текстового слоя ни на одной странице** (12/12, 12/12, 40/40). Это основной объём работы этапа 3, не ИТС.

## Печать/подпись — решено не чистить пиксели, работать через confidence

Печать на подписи — настоящая (круглая, физическая), но **задевает только строку подписанта**, не содержательный текст (проверено на 2 реальных документах — пункты/статьи ни разу не пострадали). Печать не на фиксированных координатах (положение зависит от объёма текста на странице) — детектор по координатам ненадёжен, а детектор по форме/цвету — отдельная система, которую тоже пришлось бы эмпирически проверять, при низкой отдаче (повреждается одна не самая важная строка).

**Решение**: не чистить и не угадывать повреждённый текст. Вместо этого:
1. Брать не просто текст, а `pytesseract.image_to_data` с confidence по каждому слову (проверено на реальном примере: слова под печатью дают confidence 0–55, чистый текст — 71–97, граница различима уверенно).
2. Слова ниже порога помечать как нераспознанные (например, `[нрзб.]`), не вставлять вместо них угаданный OCR-мусор.
3. Канцелярская формула перед печатью («Председатель Правительства Российской Федерации» и т.п.) предсказуема по органу-подписанту, который уже известен из `authority_name` исходного запроса этапа 1 (не угадывается по памяти, а берётся из уже подтверждённых данных) — её можно восстанавливать, а не помечать как нераспознанную.
4. **Личное имя подписанта (ФИО) — отдельный случай, не путать с формулой должности.** По двум проверенным примерам печать его не задевала, но это наблюдение на малой выборке, не гарантия на будущее. Если в каком-то документе ФИО всё же окажется повреждено: **не восстанавливать по внешним источникам/памяти, даже для высших должностных лиц, чья личность на конкретную дату формально устанавливаема** (например, кто был Председателем Правительства в такой-то год) — это прямо противоречит принципу проекта «не восполнять реквизиты не по тексту акта», применяемому во всех остальных частях этого проекта (тот же принцип, что и у референса `ker-legal-act-intake`, упоминавшегося при планировании этапа). Повреждённое ФИО — помечать как нераспознанное (`[нрзб.]`), как и любое другое слово ниже порога уверенности (см. п. 1–2 выше), без исключения для «вроде бы очевидных» случаев.

## Таблицы — главный открытый технический вопрос

Простые таблицы (повторяющаяся структура «Год/Месяц/Значение», без объединения ячеек) проверены на реальном документе (Приказ Росстандарта №901 от 13.05.2026, 62 страницы, температурные коэффициенты, 2 таблицы на странице).

**Связка Tesseract + img2table** — ненадёжна даже на этих простых таблицах: короткие числовые значения в узких ячейках (например, «11») иногда распознаются как пустая ячейка или как другое число («19»). Повышение DPI не помогает предсказуемо — на 300 DPI проблема не исчезла, а переместилась на другие ячейки.

**PaddleOCR (PPStructureV3, модель `eslav_PP-OCRv5_mobile_rec` для кириллицы)** — точнее на тексте и на отдельных таблицах, но у него найден **реальный воспроизводимый баг**: при обработке страницы с двумя и более таблицами одним вызовом полного конвейера первая (верхняя) таблица иногда распознаётся с полностью сломанной структурой (переставленные строки/столбцы, мусорные ячейки), хотя область самой таблицы определяется точно (`table 0.99` в обоих случаях). Баг **детерминирован** (два прогона одной и той же страницы дали побайтово идентичный результат — не случайность) и **непредсказуем по странице** (проверено на 4 страницах одного документа: на 2 из 4 первая таблица сломана, на 2 из 4 — нет; простой связи с положением рукописного штампа над таблицей не нашлось, гипотеза не подтвердилась).

**Рабочий обходной путь (проверен, работает)**: не отдавать всю страницу целиком. Вместо этого:
1. Один вызов — определить область каждой таблицы на странице (это работает надёжно, `table 0.99` даже там, где дальнейшее распознавание ломается).
2. Вырезать каждую найденную таблицу в отдельное изображение.
3. Распознавать каждую таблицу отдельным вызовом.

На изолированном кропе сломанная ранее таблица распознаётся корректно (мелкие огрехи: заголовок «Год» иногда читается как «Фод», разделитель дробной части — точка вместо запятой; содержательные значения — верно).

### Сложные таблицы (объединённые ячейки, многоуровневые заголовки) — проверено

Тест на реальном документе `downloads/Тест OCR 1.pdf` (стр. 14 — таблица «Таблица №1», 16 колонок, двухуровневая шапка, вертикальные и горизонтальные объединения ячеек). Документ сам по себе с текстовым слоем (это эталонный файл для сверки), но для теста страница рендерилась в PNG и отдавалась распознаванию как обычная картинка — текстовый слой исходного PDF в распознавании не участвовал, сценарий полностью эквивалентен настоящему скану без текстового слоя.

**Границы и структура ячеек (включая объединённые) определяются надёжно** — визуализация (`save_to_img`) показала точное совпадение рамок с реальной сеткой, включая корректно размеченные объединённые ячейки («100,00», «Собственные средства», растянутые на 4 подстроки). Сложность структуры (merged cells, 2-уровневая шапка) сама по себе не ломает распознавание — в отличие от бага с несколькими таблицами на странице (см. выше), здесь проблема не в этом.

Найдены два отдельных, более мелких дефекта:
1. **Встроенный экспорт в HTML (`pred_html`) даёт неровную структуру** (разное число `<td>` в разных `<tr>`) несмотря на то, что сама геометрия ячеек (judging by `save_to_img`) ровная и верная — похоже, баг именно в шаге geometry→HTML сериализации у PaddleOCR, а не в детекции. **Вывод**: не доверять `pred_html` напрямую, собирать таблицу самим по координатам ячеек (`table_res_list`/`cells_result` из JSON), а не полагаться на готовый HTML.

   **Реализовано и проверено**: `src/npa_pipeline/ocr_table.py` (`reconstruct_table`/`grid_from_cells`) — строит сетку строк/столбцов кластеризацией границ `cell_box_list`, раскладывает текст из `table_ocr_pred` по ячейкам через попадание центра текстового бокса в box ячейки, определяет `row_span`/`col_span` по размеру ячейки относительно сетки. Проверено на реальной фикстуре той же сложной таблицы (стр. 14, `tests/unit/fixtures/ocr_tables/complex_table_0.json`): собранная сетка практически полностью совпадает с документом, включая все значения, которые в сыром `pred_html` терялись или съезжали («0,78 8,315 6,00» за 2025 год, «0,73 7,816 6,00» за 2026 год и т.п. — у `pred_html` были дырами, здесь на месте). Отдельно проверено, что функция **не маскирует** случай, когда сама входная геометрия уже ошибочна (простая таблица, `simple_table_1.json` — 24 ячейки `cell_box_list` вместо верных 21 для сетки 3×7) — она не пытается угадать/исправить, а честно отдаёт результат большего размера, чем должно быть, что видно вызывающей стороне, а не тихо проглатывается. 3 юнит-теста, все на реальных фикстурах (кроме одного синтетического для rowspan).
2. **Мелкие аббревиатуры в шапке читаются с ошибками** — кириллица путается с латиницей на коротких, плотных подписях с под/надстрочными символами («НДТ» → «HДT», «т/г» → «τ/Γ», «мг/дм³» → «MΓ/∂M3$»). Числовые данные в теле таблицы при этом распознаются верно — проблема локализована именно в шапке, не в данных.

   **Реализовано и проверено**: `normalize_header_text` в `src/npa_pipeline/ocr_table.py` — словарь подтверждённых искажений (взяты дословно из реальной фикстуры, не придуманы). Два разных режима замены по соображениям безопасности: **подстрочная** — для характерных многосимвольных смесей латиницы/греческого (`HДT`→`НДТ`, `τ/Γ`→`т/г`, `MΓ/∂M3$`→`мг/дм³` и т.п.), это безопасно, такие сочетания не встречаются внутри настоящих русских слов; и **только точное совпадение всей ячейки** — для случаев, когда ключ сам по себе — обычная кириллическая буква/цифра (`"з"`→`"3"`, номер столбца в строке нумерации) — подстрочно это опасно: буква «з» входит в состав обычных слов («**В**з**вешенные**»), подстрочная замена испортила бы их. Применено на полной сложной таблице — шапка (двухуровневые заголовки, нумерация столбцов 1–16, составная фраза «снижение с мг/дм³...») теперь читается полностью верно.

### Повёрнутые страницы (landscape-таблица на странице с `/Rotate 270`) — проверено

Тест на `downloads/Тест OCR 2.pdf` — та же самая таблица (стр. 14), что и в `Тест OCR 1.pdf`, но PDF-страница хранит её с флагом `/Rotate 270` (содержимое физически развёрнуто на 90°, при открытии в обычном PDF-просмотрщике читается «книжно», сбоку). Проверено визуально: `pymupdf` уважает флаг поворота и рендерит именно так, как видел бы пользователь — текст идёт вертикально.

- **Без автоопределения ориентации** (`use_doc_orientation_classify=False`, как было в предыдущих тестах) — на удивление, текст и числа всё равно распознались в основном верно (сам детектор текста оказался частично устойчив к повороту), но часть ячеек данных потерялась по сравнению с неповёрнутой версией той же таблицы.
- **С `use_doc_orientation_classify=True` + `use_textline_orientation=True`** — PaddleOCR **сам корректно определил угол поворота** (`doc_preprocessor_res.angle == 270`, точно совпало с реальным `/Rotate` в PDF), автоматически развернул изображение, и результат практически сравнялся по качеству с уже проверенной неповёрнутой версией той же таблицы (те же мелкие огрехи в шапке, та же надёжная геометрия ячеек).

**Вывод**: поворот страниц — решённый вопрос, PaddleOCR справляется сам. В реализации нужно **всегда включать автоопределение ориентации** (`use_doc_orientation_classify=True`, `use_textline_orientation=True`) и не полагаться на то, что мы заранее прочитаем и обработаем `/Rotate` из метаданных PDF самостоятельно — модель делает это надёжнее и без дополнительного кода.

## Выбор движков — гибридная схема, обе половины проверены раздельно

Третий бесплатный кандидат (**Surya OCR**) рассматривался и отклонён — лицензия не единая: код Apache 2.0, но веса моделей (без которых код бесполезен) — модифицированная AI Pubs Open RAIL-M, бесплатна только для исследований/личного использования/стартапов с выручкой до $2–5M (источники расходятся в точной цифре), дальше нужна платная коммерческая лицензия без публичной цены. Не подходит под требование «бесплатный локальный» без оговорок, в отличие от Tesseract и PaddleOCR (оба Apache 2.0, без ограничений).

**Итоговая схема — гибридная**, обоснование эмпирическое, не теоретическое:
- **PaddleOCR (PPStructureV3) — только для таблиц.** Структура ячеек надёжна (после обхода бага с несколькими таблицами на странице), но собственная confidence у PaddleOCR **проверена отдельно и оказалась ненадёжной** — на реальной странице со штампом явный мусор (`'*'`, `'N1'`) и обрезанный печатью текст (`'Российской Федера'`) получали confidence 0.9+, наравне с чистым текстом. Для таблиц confidence не нужна — там работает сборка по геометрии (`ocr_table.py`), а не фильтрация по уверенности.
- **Tesseract — для всего текста вне таблиц.** На чистом скане распознаёт почти идеально, и его confidence (в отличие от PaddleOCR) честно отделяет текст, повреждённый печатью (0–55 на реальном примере), от чистого (71–97) — подтверждено дважды: на изолированном фрагменте строки подписи и в составе полного сквозного прогона (см. ниже).

## Реализация: `ocr_document` и сборка DOCX — проверено на реальном документе

`src/npa_pipeline/ocr.py` — точка входа `ocr_document(pdf_path, out_docx_path)`: постранично проверяет текстовый слой (страницы с текстом — копируются как есть, OCR не запускается), для страниц-сканов — рендер → `run_paddle_tables` (таблицы, через `ocr_table.reconstruct_table`/`normalize_header_text`) + `run_tesseract_text` (весь остальной текст, с подстановкой `[нрзб.]` ниже порога confidence, области уже распознанных таблиц пропускаются по bbox) → блоки сливаются в порядок чтения по вертикали → `build_docx` собирает Word-документ (таблицы — настоящие `docx`-таблицы с объединением ячеек, не текстовая имитация).

**Проверено end-to-end на реальной странице** (Постановление Правительства №691, стр. 1, та же страница из более раннего эксперимента со штампом): основной текст — без ошибок; мусор под печатью (`ЭПРОЙ`, `осСиис а` и т.п.) — заменён на `[нрзб.]`; повреждённые печатью слова канцелярской формулы («Правительства», «Федерации») — тоже `[нрзб.]`; **само ФИО подписанта распознано верно** («Д.Медведев») — именно потому, что эту часть страницы теперь обрабатывает Tesseract, а не PaddleOCR.

По пути найдены и исправлены два реальных бага (не гипотетических):
1. `pytesseract` не находил `tesseract.exe` — PATH не гарантированно содержит его в процессе (повторяющаяся особенность этой машины, см. далее). Добавлен `_resolve_tesseract_cmd()` — явный путь winget-установки как запасной вариант, если `TESSERACT_CMD` не задан и бинарника нет на PATH.
2. Из-за первого бага упавшее исключение всплывало через `tempfile.TemporaryDirectory()`, а `PIL.Image.open()` не закрывал файл явно — Windows не давал удалить временный PNG, реальная ошибка тонула под `PermissionError` при уборке. Исправлено (`with Image.open(...) as img: img.load()`).

**Восстановление канцелярской формулы должности** (п. 3 из «Печать/подпись» выше) — реализовано: `expected_signatory_title(authority_name)` отображает уже известный орган на ожидаемую формулу («Правительство...» → «Председатель Правительства...» — родительный падеж, ср.р. «-о»→«-а», подтверждено реальным документом, где именно «Правительства» стояло под печатью; «Президент Российской Федерации» → без изменений; «Федеральное агентство/служба...» → «Руководитель»). **Министерства сознательно не поддержаны** — «Министр X» требует родительного падежа названия ведомства («Министр здравоохранения», не «Министр Министерство здравоохранения»), надёжного склонения без угадывания текста нет, а реальных примеров подписи министра в этом проекте пока не было.

Замена ищется **по сквозной последовательности слов всей страницы** (`_restore_signatory_title_words`), не внутри одной уже сгруппированной Tesseract-строки — на полном 12-страничном документе выяснилось, что печать сдвигает геометрию слов настолько, что Tesseract иногда разрывает одну визуальную строку на две геометрические («Председатель [нрзб.]» / «Российской [нрзб.] Д.Медведев» — реальный случай, не гипотетический). `authority_name: str | None` — опциональный параметр `run_tesseract_text`/`ocr_page`/`ocr_document`, по умолчанию `None` (поведение не меняется, если не передан).

**Калибровка на 4 реальных документах (Постановление №691, Приказ Минприроды №814, Приказ Росстандарта №901, Федеральный закон №310-ФЗ)** вскрыла предел исходной схемы «порог confidence»: на Федеральном законе печать исказила «Президент» до «Ярезидент», но Tesseract дал этому слову confidence **73** — выше порога 60, то есть НЕ замаскировал его как `[нрзб.]`, при этом настоящая подпись «В.Путин» получила confidence **62**. Единого порога, разделяющего эти два случая, не существует (62 < 73) — confidence-подход в принципе не гарантирует 100% детекции повреждений, подтверждено на реальных данных, не гипотетически.

Для формулы должности это компенсировано: окно принимается, если каждое слово — точное совпадение, `[нрзб.]`, либо **текстово похоже на ожидаемое** (`_is_near_miss`, `difflib.SequenceMatcher`, порог схожести 0.7 — ловит «Ярезидент»≈«Президент», 0.89), и при этом среди слов окна есть хотя бы одно ТОЧНОЕ совпадение-якорь (подтверждает, что это действительно формула должности, а не случайный фрагмент текста — «Российской Федерации» само по себе часто встречается в обычном тексте документа вне подписи; проверено тестом, что такие места не портятся). Любое не прошедшее ни точное, ни нечёткое сравнение слово отменяет замену всего окна — без угадывания. ФИО подписанта по-прежнему не восстанавливается и не трогается ни при каких обстоятельствах (п. 4 «Печать/подпись» не изменился) — защита распространяется только на уже достоверно известную формулу. **За пределами формулы должности (обычный текст документа) эта защита не действует** — там confidence остаётся единственным сигналом и имеет тот же обнаруженный предел; это осознанный остаточный риск, не исправленный, см. «Вне скоупа» ниже.

13 юнит-тестов (`tests/unit/test_ocr.py`) — движки заменены фейками на реальных фикстурах, без загрузки тяжёлых моделей; включают регрессионный тест с точно воспроизведённым реальным разрывом строки у штампа, регрессионный тест на случай «Ярезидент»/«В.Путин» (с реальными цифрами confidence 73/62) и тест, что обычные вхождения «Российской Федерации» вне подписи не портятся. Отдельно `tests/live/test_ocr_document.py` (`@pytest.mark.live`, не входит в обычный прогон) — **два теста, оба зелёные на реальных сканах настоящими движками**:
1. `test_ocr_document_real_stamped_document` — **весь** 12-страничный документ (Постановление №691), 37 минут: все 12 страниц распознаны, таблиц не было, формула должности восстановилась, ФИО не тронуто.
2. `test_ocr_document_fixes_high_confidence_misread_of_president_title` — только последняя страница Федерального закона №310-ФЗ (весь 40-страничный документ ради одной строки не гоняли — слишком долго), 2 минуты 17 секунд: подтверждено на реальном скане, что «Ярезидент» в выводе отсутствует, формула «Президент Российской Федерации» восстановлена, «В.Путин» не тронут — нечёткое сравнение (`_is_near_miss`) реально работает, не только на юнит-тесте.

Отдельно всплыла и решена эксплуатационная (не связанная с корректностью OCR) проблема: на машине с 16 ГБ RAM при обработке первой страницы случается пиковая нехватка памяти (PaddleOCR лениво строит второй, отдельный движок детекции+распознавания текста специально для чтения текста в ячейках таблиц, даже когда в документе таблиц не оказалось, — дублирует самую тяжёлую часть моделей в памяти). Фоновый процесс с таким пиком системный «реапер» Claude Code по нехватке памяти аварийно останавливал в 3 из 4 попыток (включая попытки в основном потоке — не защищает). Решение — переменная окружения `CLAUDE_CODE_DISABLE_BG_SHELL_PRESSURE_REAP=1`, задана постоянно на уровне пользователя Windows (`setx`), отключает этот конкретный реапер; после этого прогон прошёл устойчиво.

**Позже найдена и устранена сама причина дублирования** (разбор исходников `paddleocr`/`paddlex`, не догадки): `PPStructureV3` безусловно строит top-level `GeneralOCR`-пайплайн на распознавание текста всей страницы — мы его результат вообще не используем (весь нетабличный текст идёт через Tesseract). Отдельно, `TableRecognition`-подпайплайн при `use_ocr_model=False` (так в его конфиге) **не** строит свой OCR-движок сразу, а делает это лениво, только по необходимости — НО у `PPStructureV3.predict()` есть параметр `use_table_orientation_classify`, по умолчанию `True` (проверка поворота каждой отдельной таблицы независимо от поворота страницы), и именно он безусловно форсирует отложенную постройку второго `general_ocr_pipeline` (`paddlex/inference/pipelines/table_recognition/pipeline_v2.py`, строки ~1221-1231) — даже когда нужные результаты OCR уже есть от top-level прохода. Передача `use_table_orientation_classify=False` в `pipeline.predict(...)` (не на уровне конструктора — там это сломало бы `lang="ru"`, см. ниже) отключает именно этот лишний движок, не трогая логику выбора моделей.

Проверено эмпирически на двух уже валидированных реальных фикстурах (не предположение): простая таблица (21 ячейка, `Приказ Росстандарта №901`) и сложная таблица с объединёнными ячейками и двухуровневой шапкой (175 ячеек/219 текстов, `Тест OCR 1.pdf` стр. 14) — `table_res_list` побайтово идентичен с `use_table_orientation_classify=False` и без него. Применено в `_default_predict_tables_fn` (`ocr.py`). Перепроверено целиком на реальном документе `Постановление №1430` (9 таблиц, 11 страниц) — структура всех 9 таблиц (размеры строк/столбцов) и восстановленная формула подписи побайтово совпали с прогоном до оптимизации; теперь при построении пайплайна грузится 11 моделей вместо 15 (пропадет самый тяжёлый дубль — `PP-OCRv5_server_det` + `eslav_PP-OCRv5_mobile_rec` + `doc_ori`/`textline_ori`). **Компромисс, не бесплатная оптимизация**: теряется детекция поворота ИНДИВИДУАЛЬНОЙ таблицы независимо от поворота страницы — такого случая (таблица повёрнута иначе, чем сама страница) в документах этого проекта пока не встречалось, принят как разумный риск.

Отдельно пробовали задать `text_detection_model_name`/`text_recognition_model_name` явно на конструкторе, чтобы выбрать более лёгкую модель детекции — **не применено**: любой заданный `*_model_name`/`*_model_dir` отключает автоподбор моделей по `lang="ru"` целиком (подтверждено предупреждением `paddleocr`), из-за чего вместо лёгкой русскоязычной `eslav_PP-OCRv5_mobile_rec` подставляется более тяжёлая общая `PP-OCRv5_server_rec` — то есть эта конкретная «оптимизация» реально делает хуже. Дальнейшей оптимизации выбора моделей (отдельно det/rec на более лёгкие варианты, вручную задавая ОБА имени, чтобы не терять `eslav`-ветку) не делали — риск регресса точности важнее неподтверждённой экономии памяти.

**`ocr_document` теперь строит движки по умолчанию лениво**, только при первой реально встреченной странице-скане, а не безусловно при вызове функции — найдено через CLI-smoke-тест (см. ниже): документ, целиком состоящий из страниц с текстовым слоем, раньше всё равно грузил все ~19 моделей PaddleOCR впустую (несколько минут); после исправления — 0.3 секунды на том же файле. Покрыто юнит-тестом (`test_ocr_document_does_not_build_default_engines_when_no_scan_pages`, через monkeypatch конструктора).

## Защита памяти (2026-10-03)

Ноутбук перезагрузился во время OCR без синего экрана: журнал Windows показал принудительное выключение без записи ошибок, заряд был 100%, дампов нет. Наиболее вероятная причина — нехватка оперативной памяти при загрузке моделей и распознавании таблиц (косвенно, без прямого подтверждения).

Теперь `ocr_document` перед каждой страницей-сканом проверяет свободную память (`psutil`, объявлен в extras `ocr`) и при нехватке останавливается с понятной ошибкой (`InsufficientMemoryError`, CLI возвращает `status: insufficient_memory`, код 1), не загружая модели. Порог по умолчанию — 2048 МБ, настраивается `--min-free-mb`, 0 отключает проверку. Покрыто юнит-тестами (подмена `psutil.virtual_memory`).

## Изоляция таблиц кропом — откатана (2026-10-03)

Пробовали: при двух и более таблицах на странице пересчитывать каждую таблицу отдельным кропом (с объединением пересекающихся bbox). Результат на реальном документе Постановления №1430: на стр. 9 одна из трёх таблиц (72 ячейки) пропадала полностью, остальные сетки не совпали с визуальным оригиналом; на стр. 8 и 6 улучшения не подтвердились. Откатано, `run_paddle_tables` снова делает один вызов на страницу.

Диагноз, который остаётся открытым: сетка строится из краёв ячеек (`reconstruct_table`, кластеризация с жёсткой толерантностью). Боксы, ужатые по тексту, дают лишние строки и столбцы (стр. 6: 9×2 превращается в 25×8). `pred_html` для того же кропа почти верный, но у него свои баги. Требуется отдельное решение (кластеризация строк по центрам текстовых строк `rec_boxes`), с проверкой на всех фикстурах.

## Абзацы и выравнивание в DOCX (2026-10-03)

Раньше каждая распознанная строка становилась отдельным абзацем. Теперь `build_docx` склеивает строки в абзацы по геометрии, которую отдаёт Tesseract (`TextBlock.x0/x1/height`):
- строка, центрированная относительно текстовой области (допуск 1.5% ширины, ширина до 95%), — отдельный абзац с выравниванием по центру;
- абзац начинается, если первая строка сдвинута от левого поля больше чем на ~5 мм (`_INDENT_MIN_PX=40` при 200 DPI), в DOCX ставится отступ первой строки по замеру;
- строка, не доходящая до правого края (больше 12% ширины), завершает абзац;
- зазор больше 1.5 высоты строки начинает новый абзац.

Проверено на реальной первой странице Постановления №1430 (Tesseract, без тяжёлых моделей): заголовок центрирован, оба абзаца получили отступ ~1,27 см, вводная строка «...постановляет:» вошла в свой абзац. Юнит-тесты на этой геометрии: `test_text_paragraphs_*`.

**Не восстанавливается (ограничение Tesseract):** жирный, курсив, подчёркивание, сноски и надстрочные индексы — по выходу `image_to_data` эти признаки не определяются. Заголовки отдельными стилями (Heading) не выставляются: надёжного признака заголовка по геометрии нет (часть заголовков набрана обычным шрифтом, верхняя строка документа выше остальных по высоте, но это не правило).

## Колонтитулы (2026-10-03)

`remove_running_headers_and_footers` (вызывается в `ocr_document` перед сборкой DOCX) убирает строки в верхней и нижней полосе страницы (6% высоты, `PageResult.page_height`), которые либо состоят только из номера страницы, либо повторяются на половине и более OCR-страниц (с учётом цифр: «Стр. 1»/«Стр. 2» — повтор). Строки вне полос и таблицы не трогаются. Проверено на реальных страницах 1–5 Постановления №1430 (Tesseract, без тяжёлых моделей): печатный код «4678924» был на каждой странице (5 раз), после очистки — 0; тело текста и подпись сохранились. Юнит-тесты: `test_remove_running_headers_*`.

## Распознавание таблиц — исследование альтернатив (2026-10-03)

Цель: максимально точное распознавание таблиц, без подстройки под одну фикстуру. Проверено, что даёт текущий набор (PaddleX/PP-StructureV3):

- **Сетка по краям ячеек** (`reconstruct_table`): ошибочна для ячеек, ужатых по тексту (Постановление №1430, стр. 6: таблица 9×2 → 23×9 с размноженными значениями). Центровая кластеризация по центрам ячеек даёт 6 строк вместо 9 и ломает объединённые ячейки (`complex_table_0`: 20×16 вместо 16×16), поэтому не годится.
- **`pred_html` и сквозная модель (`use_e2e_wired_table_rec_model`)**: на таблице 9×2 — 2 столбца верно, но строки 8 вместо 9 (одна граница пропущена). На сложной 16-колоночной таблице (Тест OCR 1, стр. 14) флаг сквозной модели не меняет результат, HTML рваный (ячеек в строках 5, 9, 11, 15, 16).

Вывод: на текущем наборе PaddleX нет варианта, который точно восстанавливает обе таблицы. Следующий кандидат — Table Transformer (TATR, MIT, веса Hugging Face): детекция строк и столбцов как отдельных объектов, а не краёв ячеек. Требует torch и transformers, которых в venv нет. Если TATR не даст нужной точности, задача выносится в отдельный этап разработки.

## Установка Table Transformer (2026-10-04)

В venv установлены: torch 2.14.1 (CPU), transformers 4.57.6 (5.x несовместим с конфигом TATR), timm 1.0.30. Веса `microsoft/table-transformer-structure-recognition-v1.1-all` (MIT) загружаются. Классы TATR: table, table column, table row, table column header, table projected row header, table spanning cell.

Важно: на Windows `import paddle` и затем `import paddleocr` в одном процессе падают с WinError 127 на `shm.dll` torch (torch подгружается через paddlex). Рабочий вариант, которым пользуется пайплайн: `from paddleocr import PPStructureV3` напрямую — проверено, `_default_predict_tables_fn()` строится. Код, использующий и TATR, и PaddleOCR, должен импортировать torch первым.

## Table Transformer — первая оценка (2026-10-04)

Структура (строки/столбцы) через TATR (`microsoft/table-transformer-structure-recognition-v1.1-all`): таблица детектируется на странице, вырезается с отступом, затем детектируются строки, столбцы и заголовки; текст — из Tesseract по центрам слов.

- Таблица 9×2 (Постановление №1430, стр. 6): 2 столбца верно; 8 строк данных разделены правильно, включая пару «Крупнейшие / Крупные», которую пропускали все варианты PaddleOCR; шапка есть, но разбита на две строки (одна пустая). Текущая сборка давала 23×9.
- Сложная 16-колоночная таблица (Тест OCR 1, стр. 14): 16 столбцов верно (PaddleOCR-сетка давала 16, но с другими ошибками, сквозной HTML — 17–20 рваных строк); строк 19, четыре пустые в шапке; значения строк данных совпадают с подтверждёнными ранее. Ошибки — распознавание текста Tesseract.

Вывод: структура TATR заметно ближе к оригиналу, чем всё, что было на текущем наборе. Следующий шаг — брать текст ячеек из PaddleOCR (`rec_boxes`), а не из Tesseract, и убирать пустые полосы шапки; проверить на обеих таблицах и на остальных фикстурах. Время работы TATR на CPU не замерено.

## TATR + текст PaddleOCR — шаги 1 и 2 (2026-10-04)

Шаг 1: текст ячеек берётся из PaddleOCR (`rec_boxes`/`rec_texts`) по центрам текстовых строк. Шаг 2: пустые строки до первого текста и внутри шапки убираются. Один и тот же файл-кроп идёт и в TATR, и в PaddleOCR.

- Таблица 9×2 (Постановление №1430, стр. 6): **9×2, текст всех ячеек совпадает с оригиналом** (значения «200001 - 600000», «10001 -40000» и т.д.). Остался один артефакт: звёздочки сносок стоят отдельной строкой перед «Небольшие…» вместо того, чтобы быть на той же строке.
- Сложная таблица (Тест OCR 1, стр. 14): 16 столбцов, 14 строк после удаления пустых (одна пустая строка-артефакт внутри), значения строк данных читаются верно. В шапке видны ошибки PaddleOCR («HДT»), которые словарь `normalize_header_text` исправляет в продуктивном пути — здесь словарь не применялся.

Пока это эксперимент вне `ocr.py`. Перед интеграцией: (а) замерить время TATR на CPU, (б) проверить на фикстурах `simple_table_0`/`complex_table_0`, (в) решить, что делать с сносками и с пустой строкой внутри таблицы.

Время на CPU: загрузка модели TATR 7.8 с (один раз на процесс); детекция строк/столбцов 0.2–0.3 с на изображение таблицы. Сам PaddleOCR для текста ячеек не замерялся отдельно — он уже есть в текущем пути.

Фикстуры:

## Интеграция TATR в ocr.py (2026-10-04)

Что сделано:
- `src/npa_pipeline/table_structure.py`: детекция регионов, строк, столбцов и объединённых ячеек (TATR, веса загружаются лениво, torch импортируется первым); чистая логика — `drop_empty_columns` (столбец без текста удаляется и учитывается в `TableBlock.dropped_columns`), `drop_empty_rows`, `merge_header_bands`, `build_cells` (объединения по классу «spanning cell»).
- `ocr.py`: `run_tatr_tables` — регион, вырезка с отступом, структура TATR, текст PaddleOCR по тому же кропу, дедупликация повторов между записями таблиц. `ocr_document(table_engine="tatr")` по умолчанию; при инъекции `predict_tables_fn` работает прежний путь PaddleOCR. TATR грузится до PaddleOCR (порядок импорта на Windows).

## Проверка на новом реальном документе (Постановление №1430, 2026-10-02)

Первый реальный прогон CLI вне уже протестированных калибровочных документов — `Постановление Правительства РФ от 15.09.2020 N 1430` (11 страниц, 9 таблиц — самый табличный документ из всех протестированных) — нашёл два новых реальных бага, не гипотетических:

1. **`InvalidSpanError: requested span not rectangular`** — на сложной реальной таблице геометрия двух ячеек даёт конфликтующие span'ы, которые `python-docx` не может представить одним прямоугольным объединением (классический «Т-образный» конфликт — одна ячейка уже объединена по вертикали, другая пытается объединить соседние по горизонтали через неё). Раньше это ронялó сборку ВСЕГО документа, теряя OCR всех 11 страниц. Исправлено (`_add_table`, `ocr.py`) — при конфликте ячейка остаётся неотъединённой (текст не теряется), не крашит сборку. Покрыто юнит-тестом через monkeypatch `docx.table._Cell.merge`.
2. **Обрезание слова печатью confidence-порог не ловил, а нечёткое сравнение (`_is_near_miss`) — тоже не ловило.** «Правительства»→«Прави», «Федерации»→«Федей» (confidence выше 60, не замаскировано) — полное сравнение `difflib.SequenceMatcher` даёт только 0.56/0.57 (разная длина режет ratio), хотя для человека очевидно, что это начало того же слова. Добавлено отдельное префиксное сравнение (`word` против среза `expected_word` той же длины, при `len(word) >= 4`) — "прави" vs "правительства"[:5]="прави" → 1.0, "федей" vs "федерации"[:5]="федер" → 0.8. Покрыто юнит-тестом с реальными словами и confidence.

После обоих исправлений — переподтверждено на том же реальном документе: все 11 страниц распознаны, формула должности восстановлена корректно («Председатель Правительства» / «Российской Федерации М.Мишустин», разрыв на две строки у штампа — тот же паттерн, что и раньше), документ собран без ошибок.

**Новая находка, не исправлена (не блокирует, но известна):** в одной из 9 таблиц двухуровневый заголовок с вертикальным объединением отрендерился как 7 одинаковых отдельных ячеек подряд вместо одного растянутого объединения — похоже, `reconstruct_table` на этой конкретной геометрии создал несколько `TableCell` с одинаковым текстом вместо одной с `row_span`/`col_span` побольше. Текст не потерян (читаемо), но визуальная структура таблицы не идеальна. Не чинили «вслепую» — нужно разбираться на конкретной геометрии этой таблицы, не гадать.

## Таблицы: переход на области PaddleOCR (2026-10-05)

TATR на страницах с несколькими таблицами (например, стр. 8–9 Постановления 1430) возвращает одну область на всю страницу, поэтому текст вне таблиц терялся. Bbox таблицы считается по фактическому содержимому ячеек, а не по области детекции.

## Текст ячеек: переход PaddleOCR → RapidOCR (2026-10-20)

При развёртывании на сервере со старым CPU (Xeon E5-2696 v2, без AVX2) обнаружен
новый SIGILL (код выхода 132) — не в TATR (тот уже чинили `torch.backends.mkldnn.
enabled = False`, см. table_structure.py), а в `_default_cell_text_fn`: нативный
`PaddleOCR(lang="ru", enable_mkldnn=False)` падает прямо на вызове `.predict()`,
несмотря на уже выставленный `enable_mkldnn=False` — то есть причина не в
MKL-DNN-бэкенде конкретно, а глубже в сборке PaddlePaddle (вероятно, часть кода
скомпилирована с расчётом на AVX2 безусловно).

Проверена замена на RapidOCR (ONNX Runtime) с моделью `eslav_PP-OCRv5_rec_mobile` —
по офиц. списку моделей RapidOCR (rapidai.github.io/RapidOCRDocs) это та же модель
PaddleOCR для восточнославянских языков, что и раньше, просто в ONNX-рантайме, с
`rapidocr>=3.10`. Сравнение на реальной таблице (Постановление №1430, стр. 6, 7
строк + шапка): текст идентичен PaddleOCR (единственное расхождение — надстрочная
«³» в «м³/сут.»: PaddleOCR потерял цифру целиком, RapidOCR сохранил её не
надстрочной — не хуже), инференс 2.02 с против 249.65 с у PaddleOCR (локально, без
GPU), и, что решающее — ONNX Runtime не падает на сервере без AVX2. Отдельно
проверено на обычном тексте страницы (не ячейки, не продакшн-путь): там RapidOCR
заметно хуже Tesseract (путает «ст.» с похожей латиницей, теряет строки) — поэтому
замена сделана только в `_default_cell_text_fn` (текст ячеек), Tesseract для
остального текста страницы не тронут.

Изменено: `ocr.py` (`_default_cell_text_fn`), `pyproject.toml` (extra `models`:
`rapidocr`, `onnxruntime`), `scripts/preload_models.py` (модель кэшируется в образ
при сборке). PPStructureV3 (структура таблиц, `_default_predict_tables_fn`) не

регионов таблиц (PPStructureV3), которую RapidOCR не заменяет.

## ИИ-эскалация: восстановление текста под печатью/штампом (2026-10-21)

Решает два пункта из «Открытых проблем» ниже («Шапка и штампы с печатями»,
«Блок электронной подписи»). Не включена по умолчанию — `--ai-escalation`
(CLI) / `use_ai_escalation=True` (`ocr_document`), т.к. требует сеть до
Ollama и заметно медленнее на страницах со штампами (VLM-инференс на CPU
сервера без GPU — десятки секунд на область, проверено).

**Два независимых вопроса про каждую найденную область** (печать/штамп/
э-подпись), а не один общий тип — выявлено на реальном примере, где
штамп регистрации Минюста перекрывает не свой текст, а чужой (см. ниже):
1. Перекрывает ли метка содержательный текст ДОКУМЕНТА, который нужно
   восстановить? Не зависит от типа метки — печать, штамп регистрации и
   э-подпись одинаково могут перекрыть текст или не перекрыть ничего.
2. Важно ли собственное содержимое метки (номер, дата, QR-код на ней самой)?
   Это отдельное, специфичное для типа решение — например, э-подпись на
   Постановлении №710 (низ стр. 1) сама по себе визуальный мусор, не несёт
   содержательной информации документа — её текст не нужен вообще, см.
   ниже.

**Механизм — два отдельных шага, не один («дёшевая эвристика + VLM
подтверждение», выбрано явно, альтернативы — всегда VLM на каждой странице
или чисто классический CV-детектор по цвету/форме — отклонены: первое
дорого там, где штампов нет вообще, второе требует отдельной эмпирической
проверки с нуля)**:
1. `mark_detection.cluster_candidate_regions` — без ИИ: печать/штамп/
   э-подпись почти всегда дают плотное скопление слов с низкой
   уверенностью Tesseract в одной области (union-find по пересечению
   bbox, раздутых на `_CLUSTER_GAP`=80px при 200 DPI). На страницах без
   таких скоплений VLM не вызывается вовсе — проверено юнит-тестом
   (`test_detect_marks_returns_empty_when_no_candidates`).
2. `ai_escalation.classify_mark` — каждый кандидат (кроп с запасом)
   отправляется в Ollama (qwen3-vl:8b) с вопросом: тип метки (печать /
   штамп_регистрации / электронная_подпись / не_метка) и перекрывает ли
   она текст документа. Ответ разбирается построчно, не JSON — устойчивее
   к тому, что VLM не всегда держит формат побуквенно
   (`_parse_classify_response`).

**Восстановление текста** (`ai_escalation.recover_covered_text`) —
промпт проверен эмпирически на 3 реальных документах (разные сканы с
печатью/подписью, перекрывающей текст подписанта): без явного запрета на
«додумывание» модель один раз добавила слово, которого не было на
картинке; с текущими правилами (только то, что физически видно,
неуверенное — `[нрзб.]`, ничего не добавлять) — 3/3 без искажений.
Применяется только к низкоуверенным словам внутри области с
`covers_text=True` (`run_tesseract_text`, `_apply_mark_escalation`) —
результат всё равно остаётся с `low=True` (выделяется в DOCX для проверки
человеком, как и обычная низкая уверенность) — ИИ-восстановление не
заменяет честную неуверенность слепым доверием.

**Проверено на реальном примере** (кроп штампа регистрации Минюста,
Приказ Минприроды №191) — показательный случай именно на «два независимых
вопроса»: `classify_mark` вернул `("штамп_регистрации", True)` —
регистрационный штамп сам по себе читаем обычным OCR («ЗАРЕГИСТРИРОВАНО
Регистрационный № 86393 от 12 января 2006 г.»), но ПОД ним проходит
отдельная, более бледная строка текста другой печати/штампа, которая
действительно перекрыта и нуждается в восстановлении — ровно то, что
предсказывала модель «перекрывает/не перекрывает» независимо от типа
метки.

**Собственное содержимое метки, не являющееся текстом документа** —
слова внутри области типа «электронная_подпись» с `covers_text=False`
исключаются из текста страницы целиком (не просто выделяются как низкая
уверенность) — пример: штамп э-подписи внизу стр. 1 Постановления №710,
визуальный мусор, явно не нужен (решение пользователя: «это просто
визуальный мусор - удалить»). Для штампа регистрации такое исключение не
применяется — его собственное содержимое (рег. №, дата) само по себе
читаемая метаинформация документа, не мусор.

Изменено: новые модули `mark_detection.py` (эвристика+детектор),
`ai_escalation.py` (клиент Ollama — восстановление текста и
классификация области); `ocr.py` (`run_tesseract_text`/`ocr_page`/
`ocr_document` — опциональные `detect_marks_fn`/`recover_covered_text_fn`,
флаг `use_ai_escalation`); `cli.py` (`--ai-escalation`);
`npa-downloader/docker-compose.yml` (сервис `ocr`: `extra_hosts:
host.docker.internal:host-gateway` + `OLLAMA_URL` — Ollama на `nv-02`
крутится в отдельном docker-compose проекте, в другой docker-сети, порт
11434 опубликован на хосте, не достижим по `localhost` изнутри другого
контейнера без этого моста; проверено `docker exec` из контейнера `ocr`).
19 новых юнит-тестов (`test_mark_detection.py`, `test_ai_escalation.py`,
+4 в `test_ocr.py`), все на фейках/реальных PNG-фикстурах — ни один не
делает сетевой вызов к Ollama (сетевая часть проверена вручную на
реальном сервере, не на CI).

**Исправлено после первого прогона на реальном сервере (та же дата)**: на
Приказе №191 через `--ai-escalation` штамп регистрации дал 9 ОТДЕЛЬНЫХ
вызовов ИИ (по одному на каждый обрывок текста — слова разных строк внутри
области метки резались на мелкие кропы независимо) и почти весь результат
оказался несвязанным мусором («4723», «НОСТРО», «ФИРОВО», «r», «40» и
т.п.) — хотя эта же модель с тем же промптом на ОДНОМ большом кропе всей
области (ручная проверка перед интеграцией) дала верный результат.
Причина — модели не хватало видимого контекста на крошечных обрезках.
Исправлено: теперь на каждую метку с `covers_text=True` — ровно один вызов
`_recover_mark_region` на всю её область целиком; возвращённые слова просто
по порядку (чтение сверху вниз, слева направо) раздаются на все исходные
низкоуверенные слова внутри этой области, независимо от того, скольким
строкам Tesseract они принадлежат (`_consume_escalated_words`) — слов не
хватило или эскалация не удалась — исходное слово остаётся как было,
ничего не теряется молча. Добавлена диагностика в stderr (количество
кандидатов, результат классификации, восстановленный текст на каждую
метку) — без неё эта проблема не была бы видна, тайминги выглядели
нормально.

**Проверено end-to-end на развёрнутом сервере после исправления** (Приказ
№191, полный документ через `--ai-escalation`, не отдельный кроп) — штамп
регистрации дал ровно один вызов ИИ (вместо 9), результат «№ 191» —
реальный, не выдуманный текст (номер приказа рядом со штампом), без
прежнего мусора. Но область метки в этом документе оказалась большой (663×
376px при 200 DPI — заголовок + сам штамп вместе) и содержит НЕСКОЛЬКО
разных фрагментов текста; модель уверенно прочитала только один из них,
остальные низкоуверенные слова внутри области (которых больше, чем слов в
ответе) остались как были — не поломаны, не заменены на выдумку, просто не
восстановлены. **Известное ограничение, не критично** (деградация
безопасная — хуже исходного необработанного состояния не становится,
просто не весь потенциал восстановления используется на больших
многосоставных областях) — если понадобится, можно разбивать крупную
область на несколько под-кропов эвристикой до эскалации, а не только
кластеризацией низкоуверенных слов целиком.

**Открытый вопрос, не решён** (не блокирует — конкретного документа-примера
пока не нашлось): штамп электронной подписи, перекрывающий часть таблицы
(не обычного текста) — по модели «двух вопросов» должен работать так же
(`covers_text=True` → эскалация), но сама эскалация сейчас подключена
только к `run_tesseract_text` (текст вне таблиц), не к тексту ячеек
(`_default_cell_text_fn`/RapidOCR) — если такой пример найдётся, потребуется
отдельная интеграция.

## Приказ №565 — ложное срабатывание TATR на блоке подписи (2026-10-22)

Новый реальный документ (Приказ Минприроды №565) выявил 4 дефекта (сверх уже
описанных выше): межсловные склейки без пробела (`join_fragment_lines`,
исправлено выше — `0 <=` в условии gap), искажения единиц измерения
(словарь `_HEADER_ABBREVIATIONS_*`, исправлено выше — `мг/нм³`/`кг/т`/`г.`),
дублирование надстрочной «³» как отдельного бокса (`_is_duplicate_fragment`,
исправлено выше) и **ложная таблица**, описанная здесь отдельно — самая
трудоёмкая, требовала исследования.

**Симптом**: конец пункта 3 приказа + строка подписи министра (нижняя часть
стр. 1) выходили в DOCX как разваленная таблица 5x12 («3 Настоящий | приказ |
вступает | B | силу | C | 1 | apra | 2024 | г. | | действует» вместо связного
предложения), а не как обычный текст. Отдельно заметно: это же объясняло,
почему штамп регистрации на этой странице не подхватывался исправлением
«штамп регистрации → мусор» (см. выше, `_apply_mark_escalation`) — весь блок
уходил через ДРУГОЙ путь (`run_tatr_tables`/`_recognize_cells`, RapidOCR на
кропах ячеек), а не через `run_tesseract_text`, где это исправление вообще
подключено.

**Диагностика на реальном сервере** (`table-transformer-detection`, та же
модель, что для `detect_table_regions`): даёт на нижней части стр. 1
score=0.862 — уверенно выше `TATR_REGION_THRESHOLD=0.7`. Проверка на другом
реальном документе (Постановление №1430, страницы 1-11) показала, что
настоящие таблицы там получают scores 0.679-0.996 — диапазон пересекается
с этим ложным срабатыванием (0.862 — между 0.679 и 0.883 у реальных
таблиц). **Поднять порог детекции нельзя надёжно** — либо потеряем реальные
таблицы, либо ложное срабатывание всё равно пройдёт.

**Исправление** — проверка уже построенной сетки (`is_plausible_table`,
`table_structure.py`), не порога детектора: настоящая таблица заполняет
большинство столбцов в большинстве строк (данные повторяются по вертикали —
измерено на 4 реальных таблицах, 0.812-0.955), а здесь «столбцы» — случайные
межсловные пробелы ОДНОЙ строки текста, заполнены лишь в 1-2 строках из 5
(измерено на реальной сетке — 0.417). Порог 0.6 — с запасом между группами.
Отклонённая область не теряется: просто не исключается из `run_tesseract_text`
(table_bboxes), попадает в обычные абзацы, как и было бы без ложного TATR-
срабатывания.

**Проверено end-to-end на развёрнутом сервере** (полный документ через
`--ai-escalation`, сравнение до/после): было 6 таблиц (включая ложную 5x12),
стало 5 (только реальные, 8x4/16x4/18x4/14x4/10x4); пункт 3 и строка подписи
теперь читаются связным текстом («3. Настоящий приказ вступает в силу с 1
марта 2024 г. и действует в течение шести лет.», «А.А. Козлов Министр»).

**Отдельное наблюдение, не блокирует**: на той же площадке (nv-02, CPU без
AVX2) при полном прогоне документа дважды подряд (до и независимо от этого
фикса) получен `SIGILL` (exit 132) без трейсбека на странице 1, без
видимого паттерна — третий прогон с `PYTHONFAULTHANDLER=1` прошёл чисто.
Уже задокументированная нестабильность этого CPU/torch-связки (см. выше,
«На CPU без AVX2 голый `import paddle` падает SIGILL»), не новая регрессия
от этого исправления — `is_plausible_table` чистый Python без вызовов
моделей, крах происходит раньше, на forward pass самой TATR-модели.
**Открытый вопрос, не решён**: причина самой флаки-природы SIGILL на этом
CPU не найдена, частота неизвестна (случилось 2 из 5 прогонов документа за
сессию) — если участится, потребует отдельного расследования (возможно,
связано с NNPACK/mkldnn на старом Ivy Bridge CPU при повторных forward pass
разных моделей в одном процессе).

Изменено: `table_structure.py` (`is_plausible_table`,
`_TABLE_MIN_AVG_COL_FILL_RATIO`), `ocr.py` (`run_tatr_tables` — вызов
проверки после `build_cells`). 3 новых юнit-теста на реальных данных с
развёрнутого сервера (`test_table_structure.py`), один существующий
синтетический тест (`test_ocr.py`) скорректирован — его диагональная
фикстура 2x2 случайно попадала под новую проверку, не относясь к тому, что
тест проверяет (offset/dropped_columns).

## Качество после фиксов (Приказ №565, 2026-10-22) — оставшиеся дефекты

После всех исправлений выше (межсловные склейки, единицы измерения,
дубликат «³», ложная таблица) полный прогон документа проверен вручную по
исходным страницам (не только по тексту) — найдены два ОСТАТОЧНЫХ дефекта,
оба не из-за кода, а из-за точности самих моделей (TATR/RapidOCR), поэтому
не исправлялись точечными эвристиками, рискующими переобучиться под один
документ:

1. **Пропуск объединения TATR на одной конкретной ячейке.** Таблица 2 (18x4,
   стр. 3 — «Электролиз в электролизерах Содерберга с боковым подводом тока
   к аноду (БТ)»): для «Серы диоксид» и «Взвешенные вещества» TATR верно
   распознал вертикальное объединение (row_span=2) между строками кг/т и
   мг/нм³ этого же загрязняющего вещества, а для соседней «Фториды твердые»
   (на той же странице, тот же повторяющийся паттерн!) — нет: дал
   row_span=1 и отдельную пустую ячейку строкой ниже. Проверено на
   реальных cells (`debug_plausibility.py`), а также локальной пересборкой
   через `_add_table` — сама сборка DOCX (python-docx merge) работает
   корректно, когда TATR действительно передаёт span; дефект строго в
   детекции структуры (`TATR_SPANNING_LABEL`), не в `ocr.py`/
   `table_structure.py`. Фикс в лоб (докидывать текст сверху вниз для
   похожих пустых ячеек) рискует испортить случаи, где ячейка пустая по
   смыслу (как «Фториды твердые» колонка кг/т на некоторых других строках
   этого документа, где значение реально отсутствует в оригинале) —
   не применялось.
2. **Разовая галлюцинация RapidOCR на одной ячейке.** Там же, группа
   «...с использованием производственной системы» (стр. 3): ячейка
   «Фториды газообразные...» дала текст с вставкой «ттпяфтонил» и
   дублированием фразы «гидрофторид, кремний» — при том, что АНАЛОГИЧНАЯ
   ячейка с тем же текстом в СОСЕДНЕЙ группе той же страницы распознана
   чисто. Сверено с оригиналом (см. `565_p4.png`/`565_p5.png`) — в
   исходнике текст не дублирован, это чистая галлюцинация движка на
   конкретном кропе, не повторяющийся паттерн.

**Статус**: оба — известные ограничения точности моделей, не блокируют
(данные не теряются полностью, остальной текст и структура таблиц верны;
похожий класс дефектов уже принят как открытая проблема ниже — «Двухуровневые
заголовки... иногда дают повторяющиеся ячейки»). Не исправлялось в эту
сессию — решение взято намеренно, не по недосмотру.

## Флаки-SIGILL — причина и смягчение через retry (2026-10-23)

Продолжение открытого вопроса выше («причина самой флаки-природы SIGILL на
этом CPU не найдена»). Точных диагностических инструментов на nv-02 так и
нет (`dmesg` — Operation not permitted, `/var/crash/` пуст несмотря на
apport, `gdb` отсутствует и на хосте, и в контейнере, `ulimit -c` — 0), но
собранных эмпирических данных достаточно для практического вывода:

- **Где падает**: всегда на САМОМ ПЕРВОМ реальном forward pass TATR
  (`microsoft/table-transformer-detection`) на странице 1 — лог обрывается
  сразу после загрузки весов модели, прямо перед первой свёрткой. Burst
  предупреждений `NNPACK.cpp:56] Could not initialize NNPACK! Reason:
  Unsupported hardware.` непосредственно перед крахом — тот же паттерн, что
  и у уже известного SIGILL на голом `import paddle` (см. выше).
- **Многопоточность — главный фактор**: контрольный замер 5 полных прогонов
  документа с настройками по умолчанию (многопоточный BLAS/OpenMP) дал 1
  крах из 5 (плюс ранее уже наблюдали 2 из 5 на другом батче — суммарно
  ~3 из 10); параллельный замер с `OMP_NUM_THREADS=1`/`MKL_NUM_THREADS=1` —
  0 крахов из 5. Гипотеза: гонка потоков при первой попытке нескольких
  потоков одновременно выбрать путь диспетчеризации векторных ядер на CPU
  без AVX2/FMA (Xeon E5-2696 v2 — есть AVX, нет AVX2/FMA).
- **Краш не повреждает ничего снаружи себя**: подтверждено напрямую — после
  упавшей (exit наблюдался и как 132 через shell, и как отрицательный
  `return_code` через `subprocess.Popen` — обычное представление сигнала)
  итерации следующие прогоны В ТОМ ЖЕ контейнере сразу проходили чисто без
  какого-либо перезапуска/восстановления. Это одноразовое падение одного
  дочернего процесса, не контейнера.

**Решено не фиксировать однопоточностью** (это надёжно убирает краш, но
ощутимо медленнее — по замерам, шаг «таблицы: структура и текст ячеек»
растягивается заметно дольше при `OMP_NUM_THREADS=1`), а **сделать падение
дешёвым и невидимым снаружи — автоповтор** (`job_runner.py`, `JobManager`):

- `JobManager` и раньше запускал CLI как подпроцесс именно ради изоляции
  (падение/OOM в подпроцессе не роняет сам сервис, см. докстринг модуля).
  Теперь `_watch` дополнительно отличает падение по сигналу
  (`return_code < 0`) от обычной ошибки и перезапускает тот же CLI-вызов до
  `MAX_CRASH_RETRIES` (2) раз вместо немедленного `failed`.
- Повтор безопасен и дёшев благодаря уже существующему постраничному
  резюму (`ocr_document`, `resume=True` по умолчанию, `pages_dir` тот же
  между попытками — путь зависит только от `--out`): CLI пропускает уже
  готовые страницы и продолжает с места падения. `_save_page` пишет
  страницу атомарно (`.part` + `os.replace`), так что крах посреди записи
  никогда не оставляет полуготового файла, который резюм принял бы за
  готовый.
- Отметка о каждом падении и повторе дописывается в журнал прогресса
  (`--- подпроцесс упал (сигнал N), повтор K/2 ---`), чтобы след не терялся
  молча; итоговое сообщение об ошибке после исчерпания повторов указывает
  число попыток.

**Проверено**: 9 юнит-тестов (`test_job_runner.py`, 3 новых — симулируют
настоящий `os.kill(SIGILL)` в дочернем процессе, не мок) зелёные на Linux
(внутри dev-контейнера, где и крутится прод-код; POSIX-only, на Windows
скипаются). Сквозная проверка через настоящий HTTP API (`/jobs`) на

поймали живьём за эти 10 попыток, чистая статистика при оценённой частоте

резюм подтверждён без регрессий).

**Открытый вопрос закрыт как «не корень, но смягчено»**: точное место в

dump, которых на сервере нет, — но для эксплуатации это больше не проблема:
падение самоизолировано, не требует восстановления, и теперь само себя
лечит повтором.

Изменено: `job_runner.py` (`Job.retries`/`authority_name`, `JobManager.
_spawn`/`_log_crash_retry`, `_watch` — цикл повторов вместо одного
ожидания, `MAX_CRASH_RETRIES=2`). 3 новых юнит-теста + обновлён docstring

## Приказ №191 — TATR путает продолжения таблиц с «повёрнутыми» (2026-10-23)

Разбор жалобы на распознавание Приказа Минприроды №191 (21 стр., сканы без
текстового слоя) показал, что на 9 из 21 страницы таблица пропадала из
DOCX целиком — не «плохо распозналась», а не нашлась вовсе на этапе
детекции региона.

**Корень**: `table-transformer-detection` (модель уровня «страница», не та,
что строит строки/колонки — см. комментарий у `TATR_TABLE_ROTATED_LABEL` в
`table_structure.py`) обучена на PubTables-1M (таблицы из научных статей),
где метка «table rotated» (label=1) означает широкую таблицу, физически
повёрнутую на 90° под портретную страницу. Продолжения многостраничной
таблицы без подписи на каждой странице (как в Приказе 191 — одна большая
таблица НДТ на 21 странице) дают тот же визуальный паттерн (высокая узкая
область от края до края без подписи) — и детектор систематически, с высокой
уверенностью (0.93–0.999 на части страниц) помечает их как label=1, а наш
код принимал только label=0 («table»), молча теряя регион. Проверены и
отброшены две гипотезы о простом геометрическом предикторе (отступ от
верхнего края, соотношение сторон bbox) — зависимости от реальной метки не
нашли, похоже на шум классификатора вне распределения обучающих данных, без
простого правила.

**Исправлено** (`table_structure.py`, `TATR_TABLE_ROTATED_LABEL`,
`TATR_REGION_FALLBACK_THRESHOLD`, `detect_table_regions`): обе метки («table»
и «table rotated») принимаются как равнозначные; если на обычном пороге
(`TATR_REGION_THRESHOLD`) ничего не нашлось, тот же forward pass (без
повторного инференса модели) переобрабатывается на пороге 0.3. Безопасность
более мягкого принятия региона обеспечивает уже существующий
`is_plausible_table` (проверка заполненности сетки ячеек на этапе структуры,
см. Приказ №565 выше) — он отбрасывает мусорные/ложные регионы независимо от
того, как регион был принят на этапе детекции; тот же механизм защитил бы и
гипотетическую будущую реально повёрнутую таблицу (OCR на неповёрнутом кропе
даст пустую/мусорную сетку и будет отброшен), не делая хуже текущего
(уже нерабочего) состояния для этого случая.

Рассмотрен и отклонён вариант подтверждения поворота через ИИ (VLM):
применялся бы широко (не точечно, как штамп/печать через
`--ai-escalation`), добавил бы задержку (десятки секунд на регион × ~20
страниц), внешнюю зависимость от Ollama и недетерминированность тестовых
фикстур — при этом `is_plausible_table` уже даёт нужное подтверждение
бесплатно и детерминированно, а реальных примеров повёрнутых таблиц для
проверки такого подхода нет.

**Проверено**: 4 новых юнит-теста (`test_table_structure_detection.py`,
фейковая модель — настоящий torch, т.к. функция безусловно вызывает
`torch.no_grad()`) + полный прогон существующего набора (97 passed) в

**Не исправлено, вне скоупа этой правки**: страницы 4,5,9,17 — регион

## Приказ №191, пункт 3 — ложные объединения ячеек TATR (2026-10-24)

Продолжение отложенного выше пункта («страницы 4,5,9,17 — модель структуры
недосчитывает...») — пользователь явно попросил разобраться. Диагноз
«недосчитывает колонки» оказался неточным: реальная причина — TATR иногда
детектирует ложную ОБЪЕДИНЁННУЮ ЯЧЕЙКУ (label=spanning) там, где на самом
деле несколько РАЗНЫХ строк с разными значениями (например, названия трёх
разных загрязняющих веществ были размечены как одна объединённая ячейка на
всю высоту трёх строк) — их текст склеивался в одну ячейку
(`assign_text`/`build_cells` отправляют текст любой строки внутри
заявленного объединения в его «начальную» позицию). Визуально подтверждено
по кропам реальных страниц (редкоземельных металлов / Карбонат натрия /
Азота диоксид — три разных строки, TATR нарисовал одно объединение на
столбец «наименование вещества»).

Отдельно подтверждено (по странице 3, последней строке перед разрывом):
первая «строка» на странице-продолжении иногда — не ложная склейка, а
настоящий перенос значения через границу страницы (значение `col1`
буквально обрывается на нижнем крае страницы 3 и продолжается на странице
4). Это не чинится фильтром объединений — отдельная, более глубокая задача
(сшивка таблицы между страницами, учитывает архитектуру — `ocr_document`
обрабатывает страницы независимо), которую решили не делать в этом заходе
(см. «Не исправлено» ниже) ради объёма работы и риска на одном документе.

**Исправлено** (`table_structure.py`, `filter_false_positive_spans`,
подключено в `ocr.run_tatr_tables` перед `build_cells`): настоящая
объединённая ячейка несёт ОДНО значение — независимый текст (посчитанный
БЕЗ учёта самого объединения, через уже существующий `cell_text_boxes`)
есть только в одной из охватываемых им позиций грид. Если независимый текст
есть в двух и более позициях — объединение ложное, отбрасывается, позиции
возвращаются к обычным отдельным ячейкам. Правило общее (не привязано к
тексту/языку/конкретному документу) — проверено на синтетических
координатах (`test_table_structure.py`, 2 новых теста: настоящее
объединение с одним значением сохраняется, ложное с независимыми значениями
по строкам — отбрасывается и текст остаётся в своих строках).

### Разбиение слишком высоких строк (2026-10-24, продолжение того же дня)

случае (страница 15) границу показали сразу и столбец «вещество», и столбец

точнее. Страница 12 вообще не изменилась (`split_oversized_rows` не нашла

| №215 | 5 | 2,3,4 | стр.1 — известный класс «ложное срабатывание TATR на блоке подписи» (Приказ №565/191, см. выше); стр.5 — `detect_table_regions` не нашёл область, проверено визуально: страница — честный хвост многостраничной таблицы (4 строки) + абзац сноски, ниже реально пусто, не дефект |
| №234 | 7 | 2,3,4,5,6,7 | стр.1 — тот же класс |
| №235 | 9 | 2,3,4,5,6,7,8,9 | стр.1 — тот же класс |

**Новый, отдельный дефект — Приказ №215, стр. 1: строка подписи
«Министр ... А.А. Козлов» пропадала из DOCX ПОЛНОСТЬЮ**, не как низкая
уверенность (`[нрзб.]`), а без единого бокса в сырых данных Tesseract.
Проверено напрямую: `pytesseract.image_to_data(..., lang='rus')` (режим
сегментации по умолчанию, `psm=3`) на полной странице не возвращает вообще
ничего — ни одного слова — ниже y≈1934 из 2332 (строка подписи физически
находится на y≈2123). На Приказах №234/235 то же самое место (тот же макет:
«Министр» слева, «А.А. Козлов» справа, большой пустой промежуток для
росписи) расположено немного ближе к основному тексту — и распознаётся
нормально, с confidence 96.

**Причина**: автоматическая сегментация страницы Tesseract (`psm=3`) иногда
вообще не находит текстовый блок, отделённый от остального текста большим
пустым полем — зависит от конкретного соотношения пустого места, не от
confidence отдельных слов (к OCR-движку в смысле распознавания символов
претензий нет, проблема на уровне сегментации страницы, до какого-либо
распознавания текста).

**Исправление** — `_recover_bottom_gap_text` (`ocr.py`), вызывается из
`_default_image_data_fn`: повторный проход Tesseract (`psm=6`, «единый блок
текста») по нижней полосе страницы, не захваченной основным проходом.
Применяется только при выполнении ОБОИХ условий:
1. Незахваченная доля высоты страницы > `_BOTTOM_GAP_RATIO` (0.08).
2. Повторный проход нашёл хотя бы одно слово с confidence ≥
   `DEFAULT_CONFIDENCE_THRESHOLD` (60) И минимум 2 буквенно-цифровых символа
   после отбрасывания пунктуации (`_BOTTOM_GAP_MIN_WORD_LEN`).

Условие 2 — не перестраховка, а необходимость, подтверждённая эмпирически:
без него на калибровочной выборке 42 реальных страниц (4 документа: №191,
215, 234, 235) ложно сработали бы 15 из 42 — Tesseract в режиме `psm=6`
уверенно (`conf` до 70) читает короткие «слова» в линиях таблицы без текста
и в росчерке подписи как случайные символы (пример: хвост росчерка подписи
на Приказе №234, стр.1, ниже уже корректно найденного «Козлов», дал «—» с
conf=70 — без фильтра по длине в документ добавился бы лишний символ).
С фильтром из тех же 42 страниц сработала только 1 — подтверждённый реальный
дефект (Приказ №215, стр.1). При срабатывании добавляются ВСЕ слова кропа
(включая соседние с низкой уверенностью) — остальной текст области получает
обычную подсветку `[нрзб.]`, как и везде в проекте для повреждённых
печатью/подписью мест.

**Проверено**:
- 3 новых юнит-теста (`tests/unit/test_ocr.py`:
  `test_recover_bottom_gap_text_adds_confident_word_from_bottom_gap`,
  `test_recover_bottom_gap_text_ignores_noise_without_confident_word`,
  `test_recover_bottom_gap_text_skips_when_gap_is_small`) — полный набор
  113 passed.
- Сквозная проверка на реальном сервере через HTTP API (Приказ №215):
  «Министр» теперь без подсветки (confidence 96), искажённый росчерк подписи
  корректно помечен жёлтым (`[нрзб.]`-подсветка), а не пропадает молча.
- Регрессии — полные прогоны через HTTP API Приказов №191, №234, №235:
  подпись на титульных страницах, где она и раньше распознавалась верно
  (№234, №235), осталась без изменений — не задвоена, не повреждена.

## Сравнение TATR и img2table на реальных документах (2026-10-24)

По запросу пользователя — системная проверка, не нужна ли замена TATR на
`img2table` (классический детектор на OpenCV + подключаемый OCR-бэкенд,
здесь — TesseractOCR) или их парное использование. Прогнано на 7 реальных
документах, 80 страниц: №215 (5), №191 (21), №234 (7), №235 (9), №565 (7),
Постановление №1430 (11), Постановление №710 (15). Для TATR — реальная
продакшн-функция `detect_table_regions` + вся цепочка сборки ячеек (не
изолированный вызов модели). Для img2table — 150 DPI (на 300 DPI детектор
линий img2table **не находит вообще ничего**, даже на чётко разлинованной
таблице — похоже, пороги толщины/длины линий у него калиброваны на
абсолютные пиксели, не на DPI; при 150 DPI находит стабильно).

**На «чистых» документах нормативов (191/215/234/235/565)** — основной объём
реального контента — у img2table не было ни разу замечено характерной для
TATR проблемы: ширина найденного региона стабильно 0.86–0.88 от ширины
страницы на каждой странице с таблицей. У TATR ширина региона «гуляет»
0.46–0.88 — и это не безобидный разброс: на Приказе №215, страницы 3 и 4,
регион TATR обрублен по правому краю (ширина региона 46% и 66% от ширины
страницы) ровно там, где начинается колонка значений нормативов
(«≤ 7,23» и т.п.) — OCR эту колонку физически не видит (её нет в кропе), и
`is_plausible_table` это пропускает (см. визуальную проверку — наложил bbox
региона на полную страницу, колонка со значениями однозначно обрезана).
Итог: TATR на этих 2 из 5 страниц молча терял **все числовые нормативы** —
самые важные данные документа — при этом таблица помечена как валидная.

**На документах со сложной/безграничной разметкой (1430, 710)** — ни один
инструмент не работает чисто:
- img2table почти бесполезен: находит содержимое лишь на 4/11 страницах
  1430 и 3/15 страницах 710, и то частично (на широких таблицах 1430
  сильно недосчитывает по сравнению с TATR).
- TATR генерирует шум: на 1430/стр.6 одна настоящая таблица (2 колонки,
  8 строк категорий очистных сооружений, визуально подтверждено) была
  задетектирована **5 раз** почти идентичными перекрывающимися регионами,
  все помечены `is_plausible=True` — без дедупликации это дало бы
  пятикратное дублирование таблицы в итоговом docx. На 710/стр.5 — чистый
  юридический текст без единой таблицы (визуально подтверждено, абзацы
  п.8–9) — TATR создал ложную «таблицу» 1×1, прошедшую `is_plausible_table`.

**Вывод**: монозамена TATR на img2table не оправдана — на сложных
документах он работает хуже, чем TATR, а не лучше. Решили не менять движок,
а точечно исправлять конкретные найденные дефекты TATR/`is_plausible_table`
(план из 3 пунктов, см. ниже; дедупликация регионов и fallback на
img2table при отклонённой/подозрительно узкой таблице — пока не сделаны,
только пункт 1).

### Пункт 1 (из 3) — `is_plausible_table` больше не пропускает вырожденные 1×1-«таблицы»

`is_plausible_table` безусловно пропускала (`return True`) любую сетку
меньше 2×2, включая буквально одну ячейку — старый юнит-тест
(`test_is_plausible_table_does_not_reject_small_grids`) даже документировал
это как сознательное решение на примере штампа нумерации страницы. На
реальных документах это позволяло случайным фрагментам обычного текста
(1430, страницы 2–4; 710, страница 5 — все визуально подтверждены) проходить
как «валидная таблица» из одной ячейки.

Исправлено: сетка 1×1 теперь всегда отбраковывается
(`src/npa_ocr/table_structure.py`, `is_plausible_table`). Остальные сетки
меньше 2×2 (одна строка из многих столбцов или один столбец из многих
строк — например, 1430/стр.5 и 710/стр.8-9, где после `drop_empty_columns`
остаётся 1 столбец на несколько строк) по-прежнему не отбраковываются этой
проверкой — осознанно, чтобы не рисковать ложным отклонением настоящих
узких таблиц без дополнительной проверки на реальных данных.

Потери контента при отклонении нет: `run_tesseract_text` (основной текст
страницы) получает список bbox только УЖЕ ПРИНЯТЫХ таблиц
(`[t.bbox for t in tables]`, `ocr.py`, `ocr_page`) — отклонённый регион не
исключается из обычного текстового прохода и распознаётся как обычный
текст страницы, а не теряется.

**Проверено**:
- Обновлены 2 существующих юнит-теста, которые раньше намеренно проверяли
  старое (ошибочное) поведение `is_plausible_table(cells, 1, 1) is True`
  — теперь `test_is_plausible_table_rejects_1x1_grid` проверяет `is False`
  на том же примере (штамп «678924»); добавлен
  `test_is_plausible_table_does_not_reject_other_small_grids` — 1×5 и 5×1
  по-прежнему принимаются.
- 2 юнит-теста в `test_ocr.py` (`test_run_tatr_tables_drops_duplicate_texts_from_overlapping_table_entries`,
  `test_run_tatr_tables_recognizes_each_cell_separately_when_cell_fn_given`)
  использовали синтетическую структуру, которая после `drop_empty_columns`
  случайно схлопывалась до 1×1 — не по сути теста (дедуп дублей текста,
  раздельный OCR ячеек), а из-за того, что второй столбец фикстуры был
  пустым. Поправлены добавлением текста во второй столбец; сам тестируемый

- Полный набор: 114 passed (было 113, +1 новый тест).
- Реальные документы, целевые страницы, до/после:
  - 1430, стр. 2–4: было `n_rows=1 n_cols=1 is_plausible=True`, стало
    `is_plausible=False` — на всех трёх.
  - 710, стр. 5: было `is_plausible=True`, стало `is_plausible=False`.
  - Соседние НЕ-1×1 случаи остались как были (регрессии нет): 1430/стр.5
    (`n_rows=2 n_cols=1`), 710/стр.8-9 (`n_rows=3..6 n_cols=1`) —
    по-прежнему `is_plausible=True` (вне скоупа этого пункта, см. выше).
  - 1430/стр.6 (баг дублирования региона) — как и ожидалось, не затронут
    этим фиксом (там все 5 регионов 2-колоночные, не 1×1) — это пункт 2

### Пункт 2 (из 3) — дедупликация перекрывающихся регионов TATR

DETR-детектор TATR (`detect_table_regions`) не гарантирует одну рамку на
объект — в отличие от классических детекторов с NMS, set-based предсказание
DETR может выдать несколько почти идентичных боксов на одну и ту же таблицу,
и `post_process_object_detection` из transformers это не фильтрует. На
Постановлении №1430, стр. 6, одна настоящая таблица (2 колонки, 8 строк
категорий очистных сооружений) была найдена 5 раз почти идентичными
перекрывающимися регионами — без слияния каждый обрабатывался бы и
вставлялся в docx отдельно (пятикратное дублирование таблицы).

Исправлено: `detect_table_regions` теперь сливает перекрывающиеся регионы в
их общую охватывающую рамку (`_merge_overlapping_table_regions`,
`src/npa_ocr/table_structure.py`) — итеративно, пока есть пары с IoU > 0,
так что и цепочки частично перекрывающихся боксов (A перекрывает B,
B перекрывает C, A и C не пересекаются напрямую) сливаются в один. Та же
идея уже применялась к выходу PaddleOCR (`_merge_overlapping_regions` в
`ocr.py`) — здесь отдельная копия в `table_structure.py`, чтобы не заводить
обратную зависимость `table_structure.py -> ocr.py` (сейчас зависимость
только в одну сторону: `ocr.py` импортирует `table_structure`).

**Проверено**:
- 3 новых юнит-теста (`tests/unit/test_table_structure.py`):
  `test_merge_overlapping_table_regions_collapses_real_duplicate_detections`
  (реальные координаты всех 5 боксов с 1430/стр.6 — сливаются в одну рамку
  `(209, 968, 1380, 1647)`), `test_merge_overlapping_table_regions_keeps_separate_tables_apart`
  (две геометрически непересекающиеся области остаются раздельными),
  `test_merge_overlapping_table_regions_passes_through_single_region`.
- Полный набор: 117 passed (было 114, +3).
- Реальные документы:
  - 1430, стр. 6: было 5 регионов (все `plausible=True`), стало 1 регион
    `[209, 968, 1380, 1647]`, `n_rows=9 n_cols=2` — совпадает с визуально
    проверенной структурой таблицы (заголовок + 8 строк категорий).
  - 1430, стр. 5 (3 региона: 1 настоящий + 2 перекрывающихся друг с другом
    мусорных) — стало 2: непересекающийся с остальными регион остался
    отдельно, два перекрывавшихся друг с другом слились в один — подтверждает,
    что слияние не затрагивает геометрически различные области.
  - 1430, стр. 9 (была изначально 1 область) — не изменилось, регрессии нет.
  - 710, стр. 1 (было 3 региона, частично перекрывающихся по вертикали) —

### Пункт 3 (из 3) — fallback на img2table для подозрительно узких регионов TATR

Приказ №215, страницы 3-4 (см. «Сравнение TATR и img2table...» выше): регион
TATR обрезан по правому краю, колонка со значениями нормативов не попадает
в OCR-кроп, таблица при этом проходит `is_plausible_table` — самая серьёзная
из трёх находок сравнения, прямая потеря регуляторных данных, а не просто
кривая структура.

**Решено НЕ делать fallback при отклонении TATR** (`is_plausible_table=False`),
хотя в постановке задачи рассматривались оба триггера. Причина — реальный
контрпример: на Приказе №215, стр. 1 (блок подписи министра, TATR корректно
отклоняет) img2table нашёл СВОЮ ложную «таблицу», приняв за неё обычный абзац
текста постановления. Запуск img2table на каждой отклонённой TATR странице
добавил бы новый источник ложных срабатываний без подтверждённой пользы — на
реальных отклонённых случаях (1430, 710) img2table почти везде тоже находит
только пустоту, значит, выгоды для этих документов от такого триггера нет, а
риск (215/стр.1) подтверждён. Второй триггер — подозрительно узкий ПРИНЯТЫЙ
регион — остаётся, он и есть собственно пункт 3.

Реализовано (`src/npa_ocr/ocr.py`): у каждой принятой (`is_plausible=True`)
таблицы считается правый отступ — доля ширины страницы правее итогового bbox
таблицы. Если отступ превышает `_IMG2TABLE_RIGHT_MARGIN_THRESHOLD = 0.20`
(откалибровано на тех же данных сравнения: у «нормальных» таблиц, включая
легитимно широкие безграничные таблицы Постановления №1430, отступ не
превышал 0.17; у двух реальных обрезанных страниц — 0.23 и 0.43), на ВСЕЙ
странице (не на узком кропе TATR — переиспользовать его бессмысленно: колонки,
которой нет в кропе, другой OCR-движок не восстановит) запускается
независимый проход `img2table` (TesseractOCR-бэкенд, 200 DPI — та же
плотность, что и у основного пайплайна; специально проверено, что в отличие
от 300 DPI на этом разрешении img2table таблицы находит, см. docs/plan.md
выше). Среди найденных img2table таблиц выбирается та, что по вертикали
соответствует региону TATR (`_best_img2table_match`, минимум 30% перекрытия
высот — страхует от похожей по высоте, но другой таблицы на той же странице).
Если у неё структура ШИРЕ, чем у результата TATR — таблица TATR заменяется
целиком (ячейки, число строк/столбцов, bbox) на найденную img2table; если нет
— результат TATR остаётся как есть. Объединённые по вертикали/горизонтали
ячейки img2table (он не отдаёт row_span/col_span напрямую — см.
`_table_cells_from_img2table`) определяются по повторяющемуся bbox в сетке.

Добавлена зависимость `img2table>=2.0` в extra `models` (`pyproject.toml`) —
не обязательная: при отсутствии библиотеки fallback просто ничего не находит
(`ImportError` перехватывается), как и при любой другой ошибке распознавания
img2table — это необязательный cross-check, а не основной путь.

**Проверено**:
- 7 новых юнит-тестов (`tests/unit/test_ocr.py`):
  `test_table_cells_from_img2table_builds_flat_grid_without_merges`,
  `test_table_cells_from_img2table_merges_repeated_bbox_into_span`,
  `test_best_img2table_match_picks_candidate_with_largest_vertical_overlap`,
  `test_best_img2table_match_returns_none_below_overlap_threshold`,
  `test_run_tatr_tables_uses_img2table_fallback_when_region_is_clipped`,
  `test_run_tatr_tables_keeps_tatr_result_when_img2table_candidate_is_not_wider`,
  `test_run_tatr_tables_does_not_call_img2table_fallback_when_region_is_not_clipped`

захваченный мусор» и «вероятно настоящий текст шапки, задетый по краю» —
требует более точной геометрии области или повторного запроса к VLM
отдельно по перекрывающейся части) — отдельная, непростая задача, не
делалась в этой сессии.

### Частично исправлено (2026-10-25): защита от потери настоящего текста при эскалации; `--ai-escalation` включена в веб-приложении по умолчанию

Решает только РЕГРЕССИЮ из предыдущего раздела (потерю «И ЭКОЛОГИИ»), не сам
просачивающийся мусор штампа — см. «Вывод» выше, это осознанно не то же самое.

**Фикс**: перед тем как раздавать слова, восстановленные VLM, по словам
метки — сравниваем количество слов, которые реально вернула VLM, с
количеством низкоуверенных слов (центр bbox), которые геометрически попадают
в границы этой конкретной метки (`_count_points_in_box` в `ocr.py`). Если
VLM вернула МЕНЬШЕ слов, чем нужно заполнить — считаем всю эскалацию для этой
метки неудачной (не подставляем ничего, не только «не хватило слов на
хвост» как раньше), исходные слова остаются как были, с пометкой низкой
уверенности для проверки человеком.

Отвергнутый вариант: защита «не трогать строку, если в ней есть хоть одно
высокоуверенное слово-соседи» — ломает ранее подтверждённый реальный случай
(Постановление №710, строка подписи «Председатель [нрзб.→Правительства]
Д.Медведев» — там строка смешанной уверенности и эскалация должна работать).
Обе реальные метки (710 и 215) дают смешанную уверенность на уровне строки —
строчный сигнал их не различает, поэтому защита сделана на уровне метки и
по количеству слов, а не по соседству.

Проверено: новый юнит-тест на фейковом VLM-ответе короче, чем нужно
(`test_run_tesseract_text_rejects_escalation_answer_shorter_than_low_word_count`,

Встраивание результатов спайка `npa-vlm-ocr` (план там же: `docs/integration-plan.md`).

- **Этап 1 — `vlm_tables.py`**: DeepSeek-OCR по всей странице (vLLM на GPU nv-02, ~7 с на страницу
  против 3–9 мин у TATR + PaddleOCR на CPU) + структура таблицы по линиям скана, текст ячеек от
  DeepSeek; для таблиц без линий в теле — HTML DeepSeek как есть. На всех 117 таблицах спайка итог
  совпадает со спайком.
- **Этап 2 — поворот страницы по Tesseract OSD** (`auto_rotate=True` по умолчанию, CLI
  `--no-auto-rotate`): альбомные таблицы в книжном скане (Приказы №227, №228) лежали на боку, и их
  не читали ни Tesseract, ни модели таблиц. Страница-скан поворачивается сразу после рендера, до
  таблиц и текста — для любого `table_engine`. Порог уверенности OSD 2.0: на 179 страницах спайка
  повёрнуто 17 (все — действительно на боку или вверх ногами), ни одной ровной. Цена — один вызов
  OSD (~0,5 с, замер на 3 страницах) на страницу-скан. `auto_rotate` входит в параметры сохранённых страниц, поэтому
  прежние сохранённые прогоны пересчитываются.
- **Этап 3 — `table_engine="vlm"`** (CLI `--table-engine vlm`, для HTTP API — переменная
  `NPA_OCR_TABLE_ENGINE`): таблицы страницы — `run_vlm_table_blocks`, текст вне таблиц — Tesseract,
  как у `tatr`. Если DeepSeek взял HTML без линий в теле, его рамка охватывает только шапку —
  `extend_to_rows` продлевает её вниз по строкам Tesseract, совпадающим со строками таблицы по
  порядку (иначе тело таблицы попало бы в текст второй раз; 1430 стр. 8). vLLM не ответил
  (`VlmUnavailable`) — до конца документа таблицы идут через `tatr`, причина записывается шагом в
  тайминги. GPU общая, поэтому vLLM стоит за шлюзом `vlm_gate.py` (сервис `vlm-gate` в
  npa-downloader). Шлюз поднимает контейнер по первому запросу и останавливает после
  `VLM_IDLE_MIN` (10) минут без запросов. Доступ к docker — через `docker.sock`, а это права root на
  хосте, поэтому порт шлюза наружу не публикуется.
  Прогон 14 документов спайка (179 страниц) через `/jobs` на nv-02 занял 53 мин, всё готово, ни
  одного отката на `tatr`. На каждую страницу ушло: DeepSeek ~4 с, сетка ~1 с, OSD ~2 с, Tesseract
  ~2 с. Холодный старт vLLM через шлюз — 93 с, на первой странице первого документа. Остальное
  время заняла ИИ-эскалация печатей (Ollama), которая в сервисе включена. Например, у №156
  эскалация — ~250 с из 349. Все 117 таблиц спайка совпали по форме и тексту ячеек (3409 ячеек, без
  дочитки этапа 5). Шлюз остановил vLLM через 10 мин после последнего запроса.
- **Этап 4 — сшивка таблиц между страницами** (`table_stitch.py`, `stitch_tables`; только для
  `table_engine="vlm"`, пороги проверены на рамках `vlm_tables`). Продолжение: последняя таблица
  страницы доходит ниже 80% высоты, первая таблица следующей OCR-страницы начинается выше 15%, число
  столбцов одно. Убирается повтор шапки или нумерации столбцов, хвост строки, разрезанной страницей
  («монооксид)», «(исключая метан)»), дописывается в последнюю строку, а объединение, продолжающееся
  на новой странице, продлевается. Перед страницей-продолжением в DOCX нет разрыва страницы: без
  этого таблица на 18 страниц (№191) оставляла за собой 17 пустых. На страницах прогона этапа 3 сшивка
  совпадает со спайком: 117 таблиц → 40, те же страницы, формы и объединения, текст ячеек отличается
  только в дочитанных спайком (этап 5). DOCX №191: 21 таблица → 2, разрывов страниц 20 → 1.
- **Этап 5 — дочитка сомнительных ячеек** (`vlm_reread.py`, в `table_engine="vlm"` всегда).
  Сомнительные ячейки сетки: текст только от Tesseract, «чернила» без текста, текст DeepSeek не похож
  на Tesseract. Кроп ячейки идёт в DeepSeek-OCR («Free OCR.», вертикальный текст — повёрнутым, сторона
  по logprob). Если ответ негоден — пара с соседней ячейкой слева, затем запрос на markdown. Ответ
  принимается только прочитанным: формулы, латиница вместо кириллицы и неуверенный текст в ячейке
  без Tesseract отбраковываются. Текст DeepSeek заменяется лишь уверенным ответом, который ближе к
  Tesseract. Принятый текст снимает жёлтую пометку, время — шаг «таблицы: дочитка ячеек (vLLM)».
  Страницы, сохранённые до этапа 5 с `vlm`, пересчитываются (`vlm_version` в параметрах).
  Сверка на живом vLLM по сохранённым ответам DeepSeek на страницы спайка: 117 таблиц, 3541 ячейка,
  расхождений со спайком 0, сомнительных 156, дочитано 132 — как в спайке. Тесты проигрывают ответы
  модели, записанные на этой сверке (ключ — sha1 пикселей кропа). Какие ячейки сомнительны, зависит
  от версии Tesseract: Windows-сборка читает «H₂SO₄» как «Н›$О1», и ячейка 191 стр. 14 становится
  сомнительной, а Tesseract 5.5 в образе — нет.

## Штампы, печати, подписи: чистка меток по трём прочтениям (2026-10-27)

Решение пользователя: текст штампа, печать и подпись — мусор, выкидываются целиком; текст
документа под ними и рядом остаётся. Прежняя эскалация (кластеры неуверенных слов + один ответ
qwen3-vl на область, раздаваемый по словам) на этом не справлялась: мусор штампа Минюста оставался
в шапке приказов (215, 248), а на 428-р печать испортила слова при уверенном Tesseract, и эскалация
не запускалась вовсе. Сканы — в градациях серого: отделить печать по цвету нельзя.

Спайк — npa-vlm-ocr `marks/README.md` (56 страниц 14 документов: первая, вторая, средняя и
последняя страница-скан). Модуль `vlm_marks.py`, путь `table_engine="vlm"` + `use_ai_escalation`:

- qwen3-vl (Ollama, `"think": false` — с рассуждениями однажды думал 450 с и ответил пусто) даёт
  рамки меток: штамп регистрации и штамп электронной подписи, печать, подпись. На 42 страницах без
  меток — ни одной рамки, на первых страницах всех 14 документов — все метки. ~11 с на страницу,
  поэтому зовётся не везде (`should_locate`): первая и последняя страница, скопление неуверенных
  слов (`mark_detection.cluster_candidate_regions`), картинка DeepSeek не на месте герба.
- DeepSeek-OCR (тот же ответ на страницу, что и для таблиц) текст меток почти не читает и читает
  слова сквозь оттиск печати — опора для слов у меток. Заменять им Tesseract нельзя: на 215 он
  пропустил «ЭКОЛОГИИ» под краем штампа. Режим «Locate <|ref|>stamp<|/ref|>» метки не находит.
- Правила (`clean_lines`, подробно — docstring модуля): подтверждение DeepSeek — только блоком,
  лежащим там же, где слово; в штампе слово остаётся, только если продолжает печатную строку
  документа и штамп в строке ещё не начался (после черты рамки «|» — всё штамп); в рамке подписи
  или печати — подтверждённое или уверенное печатное слово; шапка у штампа, начатая как название
  органа, дописывается по `authority_name` (край штампа портит «ЭКОЛОГИИ» на 9 приказах из 11).
  Заменённое и дописанное — жёлтое.
- Ollama недоступна — до конца документа без чистки (`метки: Ollama недоступна` в таймингах).
  Страницы, сохранённые до чистки меток, пересчитываются (`marks_version`).

npa-downloader передаёт `authority_name` и для приказов министерств («Приказ Министерства X от» →
«Министерство X»). Тесты — `test_vlm_marks.py` на словах Tesseract 5.5, ответах DeepSeek и qwen3-vl,
записанных на nv-02 (12 страниц), и два сквозных в `test_ocr.py`. Проверено через веб-приложение
(215, 565, 1430): метки выкинуты, шапки и строки подписанта целы, qwen3-vl — 8–33 с на страницу,
только на 2–3 страницах документа.

Не исправлено: 191 стр. 1 — рамка qwen захватила только низ штампа, в тексте остаются «{Е», «и Е»;
одиночная буква от черты рамки чуть правее рамки qwen (376 стр. 1). Найдено попутно, к меткам не
относится: в сноске 565 стр. 7 строка с широкими пробелами разбита на куски, идущие в обратном
порядке («окружающей среды, / области охраны / регулирования в / государственного»).

## Вне скоупа этапа 3 (пока)

- ИТС-приказы Росстандарта (см. «Охват» выше).
- Чистка печатей/подписей на уровне пикселей.
- Восстановление формулы должности для министерств («Министр X») — не поддержано, требует склонения названия ведомства, см. «Реализация» выше.
- Калибровка порога confidence (60) — сделана на 4 реальных документах (не на одном); нашла реальный предел подхода (confidence не ловит 100% повреждений, см. «Реализация» выше) и частично компенсирована нечётким сравнением, но только для уже известной формулы должности, проверено и живым прогоном. **Остаточный риск вне формулы не устранён** — обычный текст документа по-прежнему может содержать слова, искажённые печатью с confidence выше порога, без способа это поймать; сам порог 60 не менялся.
- Веб-ручка над `ocr_document` — реализована через фоновое задание в отдельном процессе (см. «Веб-интеграция»).
- Дальнейшая оптимизация выбора моделей PaddleOCR (лёгкий det/rec вместо server-tier, с явным заданием ОБОИХ имён, чтобы не потерять `eslav`-ветку языка) — не делали; `use_table_orientation_classify=False` (безопасная оптимизация, устраняющая дублирование движка) уже применена, см. «Реализация» выше.
